# Аналіз Nectar.css та варіанти покращення

## Короткий висновок
Проєкт має сильну базу для classless-фреймворку: читабельні токени теми, підтримка автоматичного/ручного dark mode, базове покриття основних HTML-елементів та зрозумілий demo. Водночас є потенціал для покращення в доступності, консистентності API змінних та якості документації.

## Що вже добре
- Тема побудована на CSS-змінних у `:root`, що спрощує кастомізацію і темінг.
- Є і системний (`prefers-color-scheme`) і ручний (`.dark-theme`) сценарій темної теми.
- База типографіки, форм, таблиць, медіа та базових елементів вже охоплена.
- README двомовний і містить швидкий старт.

## Ключові зони для покращення (пріоритет)

### P1 — Доступність (a11y)
1. **Додати стилі `:focus-visible`** для посилань, кнопок і полів форми (зараз є `:focus` для форм, але не для links/buttons).
2. **Додати підтримку `prefers-reduced-motion`** і відключення/зменшення transitions для користувачів з чутливістю до анімацій.
3. **Перевірити контрастність кольорів** (особливо visited links у dark mode та допоміжні кольори типу `#888`, `#666`).

### P1 — Узгодженість API змінних
4. **Уніфікувати назви CSS-змінних у README і у фреймворку**:
   - README показує `--bg`, `--text`, `--link`, `--button-bg`, `--max-width`.
   - У коді використано `--backgroundColor`, `--foregroundColor`, `--linkColor`, `--submit-bg-start`/`--submit-bg-end`, `--maxWidth`.
   - Варіант: або документувати реальні токени, або додати alias-змінні для сумісності.

### P2 — Архітектура стилів
5. **Прибрати дублювання dark theme-токенів** між `@media (prefers-color-scheme: dark)` і `:root.dark-theme` через спільний шар/селекторну стратегію.
6. **Додати CSS cascade layers (`@layer`)** для більш контрольованої специфічності (base/components/utilities).
7. **Нормалізувати неймінг** (camelCase vs kebab-case) для кращої переносимості і передбачуваності.

### P2 — Документація та DX
8. **Додати секцію Browser Support + Known limitations** (що покривається, що ні).
9. **Додати changelog + версіонування** (навіть простий `CHANGELOG.md` і semver-теги).
10. **Додати “copy-paste themes”** (мінімум 2-3 готові теми: light, dark, high-contrast).

### P3 — Якість і автоматизація
11. **Додати stylelint + форматер** (базова перевірка стилю, порядок властивостей).
12. **Додати візуальні smoke-тести** (наприклад, Playwright screenshot diff для `demo.html`).
13. **Додати CI** для lint + збірки мінімізованої версії + перевірки ваги файлу.

## Пропонований roadmap

### Фаза 1 (1-2 дні)
- `:focus-visible` для інтерактивних елементів.
- `prefers-reduced-motion`.
- Оновлення README: правильні назви токенів.

### Фаза 2 (2-4 дні)
- Рефакторинг dark-mode блоку без дублювання.
- Підключення stylelint + базовий CI workflow.
- Додавання `CHANGELOG.md`.

### Фаза 3 (3-5 днів)
- Візуальні regression-тести для demo.
- Розширена документація: browser support, accessibility notes, recipe-секція з темами.

## Швидкі “win” задачі (мінімум ризику)
- Додати `:focus-visible` і не прибирати системний outline без альтернативи.
- Додати `@media (prefers-reduced-motion: reduce)`.
- Синхронізувати README-токени з реальними змінними CSS.

## Метрики успіху
- Lighthouse Accessibility: +5-15 пунктів на демо-сторінці.
- Відсутність regressions у візуальних скріншотах demo.
- Менше питань користувачів щодо кастомізації завдяки узгодженій документації змінних.
